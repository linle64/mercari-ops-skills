# Mercari 台账与对账

台账是这门生意的账本：哪件在哪个号、多少钱、货源是谁、卖没卖，全以台账＋实时核查为准，不靠记忆。

## 文件（工作区 `hidden_files/`）

- `listed.json`：已上架台账（m 编号、账号、价格、货源 ID、状态 listed/sold/delisted）。历史条目的账号字段写法可能不统一，判断账号以登录态实查为准。
- `drafts.json`：草稿台账。
- `pool.json` / `pool_pdd.json`：候选池（status 会滞后，见 mercari-select）。
- **改任何台账 JSON 前先备份**，命名沿用 `<文件>.bak-<日期>-<轮次>`；改完校验 JSON 格式有效。

## 登记口径

- 发布成功 → listed.json 追加一条（m 编号、账号、标题、价格、货源平台＋ID、上架日期）。
- 建草稿 → drafts.json 登记；草稿发布后从 drafts 迁到 listed。
- 售出 → 状态改 sold，补买家、成交价、售出时间；取引状态变化（已发货／受取評価待ち／完了）在运行日志里更新。
- 删除 → 状态改 delisted，保留条目不物理删（审计需要）。

## 对账节奏（轻量化定版）

- **每日**：只查下書き一覧的消失情况（草稿被发布／删除的信号），不做全量出品中对账。
- **全量对账**：只在固定日（如周五），或人工回报已自行发布草稿时做——两号出品中列表与 listed.json 逐条比对，差异当场修正台账并在日志里列明。
- 操作者可能在对话之外自己发布草稿或改价：汇报库存数字前先查实时列表，实时状态优先于记录里的最后状态。

## 观察与改价规则

- 7 天零浏览：改标题或降价（改价流程见 mercari-listing，方案先报人工）。
- 30 天零成交：进入下架评审。
- 値下げ依頼：不自动答应，汇总给人工决定（见 mercari-comments）。

## 删除评审标准

评审维度：上架时长、浏览量、いいね数、评论数。实证判例口径：上架一周以上、浏览 ≤37、评论 0 的低流量件列建议删；零赞件另列。
- **有评论的商品先不删**，单独列出等决定——哪怕数据再差。
- 同款两号都有的，评审时成对列出并给建议（如删数据差的那一号那件），不自作主张。
- 评审报告写 `hidden_files/del-review-<日期>.md`；批准后执行删除，执行日志 `del-run-<日期>.md`，台账同步标 delisted 并备份。
- **删除是独立授权动作**：有评审报告不等于有删除许可，必须等明确批准删哪几件。
